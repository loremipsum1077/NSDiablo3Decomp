# Lua-only compiler integration

The normal build remains upstream clang 5.0.1. Select the recovered Lua backend explicitly:

```sh
python3 tools/build.py --lua-compiler
```

Prepare explicitly before a game build:

```sh
python3 tools/bootstrap.py --prepare-toolchain --allow-downloads
python3 tools/backends.py --prepare-lua --allow-downloads
python3 tools/backends.py --check
```

For offline Lua preparation, supply `--archive /path/to/llvm-5.0.1.src.tar.xz`
and omit `--allow-downloads`; both images must already be ready. Archive size and
SHA-256 must match [`../llvm.lock.json`](../llvm.lock.json); its
[authentication limits](../llvm-downloads.md) still apply. Preparation uses the
existing Docker/GCC workflow, AArch64-only assertion-enabled Release configuration
and pinned patch. `--jobs 6` selects bootstrap parallelism. Ordinary builds never
implicitly download a backend. `tools/build.py --lua-archive PATH --lua-compiler`
remains an explicit offline preparation shortcut.

Caches live at `build/lua-backends/<recipe-and-platform-hash>`. Recipe upgrades
select a new directory; existing and incomplete caches are never overwritten or
removed. `python3 toolchain/backend.py --path` prints the default cache path.
Every compilation checks recipe/configuration, patch, configure options, executable
hash and host architecture. Readiness also checks image recipe/installed bytes and
runs `llc --version` offline. These are local provenance checks, not independent
approval of the builder or proof of reproducible package inputs.

To reuse an existing matching cache without recompilation:

```sh
python3 tools/backends.py --adopt-lua /path/to/existing/cache
```

Adoption validates all current cache checks and copies the binary and original
receipt unchanged. An
explicit `D3_LUA_TOOLCHAIN=/path/to/cache` selects exactly that cache, with no fallback;
CMake binds the validated selection into its launcher and object dependencies.
Receipt builds accept an explicit `--lua-cache` or resolve the same default key.
Keep explicit old paths and old receipts for their original revisions. A stale
cache is not repaired by editing its receipt. For a corrupted occupied default key,
readiness prints a preservation-first move command; choose an unused preservation
path if that destination exists, then explicitly prepare again.

The middleware target's C launcher recognizes only C files directly under
`src/Contrib/Contrib/lua/src`. Other compile commands execute unchanged. For
Lua it preserves the normal clang frontend command, includes, definitions,
unsigned-char setting, debug paths and Ninja dependency generation, then feeds
textual LLVM IR to the pinned backend. Explicit `-function-sections` preserves
the normal object's section policy, because that driver option does not travel
through LLVM IR. Object paths and link-map owner names remain unchanged.
Each Lua object has adjacent `.ll` and `.commands.json` artifacts with command
lines and hashes. Header depfiles remain generated by clang; compiler recipe
files, receipt and backend are also explicit object dependencies.

Run the ordinary project checker after the linked build. The integration does
not promote inventory entries or guarantee every function matches.

To return to the upstream backend:

```sh
python3 tools/build.py
```

Every invocation explicitly configures `D3_LUA_COMPILER=ON` or `OFF`, so switching
modes cannot leave the prior mode selected in CMake's cache. `--clean` and
`--reconfigure` retain their normal meanings. Direct CMake users must bootstrap
first and explicitly set `-DD3_LUA_COMPILER=ON` inside the derivative image.
