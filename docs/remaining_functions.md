# Remaining functions

Every function in the game binary that does not yet match byte for byte, with a short reason and whether the difference matters for how the game behaves. Generated by `tools/remaining_report.py` at commit `e6a8c60c` (comparison data `build/status/equiv.json` from `e6a8c60c`). The full list is [remaining_functions.csv](remaining_functions.csv); this page is the summary.

**650 functions, 858,036 bytes**: 627 written but not matching (M), 4 written but not matching and outside the comparison report (W), 8 not written (U), and 11 excluded functions that carry a category (L). Plain excluded library code (FMOD, 2,180 functions) is not listed; see [library_functions.md](library_functions.md).

MattersForGame: **624 no**, **26 possibly**, **0 yes**.

Of the 9 unwritten (U) functions, 8 are template or lambda code whose source is written: our build inlines it into its caller or emits it under a different lambda number, so the game still has the code; they are marked `no` (or `possibly` where the instance's user is unknown) rather than `yes`. Only `UI_Input` is genuinely missing.

## Terms

- **Tier**: how close a written function is, measured automatically by `build/status/equiv.py`. *regalloc*: the same instructions, only the registers differ. *equivalent*: the same calls in the same order and nearly the same instructions, so it behaves the same by a heuristic. *close*: similar, with real differences left. *draft*: rough. **The tiers are a heuristic, not a proof**, so `no` below means "no known behavioural difference", not "proven identical".
- **Register allocation**: the compiler's choice of which CPU register holds each value.
- **Inlining**: copying a small function's body into its caller instead of calling it.
- **MattersForGame**: `no` = written and, as far as is known, behaves like the original (or the difference is a limit of the comparison tool); `possibly` = written but not shown to behave the same (a real operation difference, a missing or extra call, an unidentified statement, or a rough draft); `yes` = missing code the game needs.
- **Reason source**: where each row's cause came from. source comment: 339, area (LibTom/Lua): 254, notes: 26, override: 17, excluded_functions.csv: 11, tier: 3. "tier" means no note named the function and the cause is read from the tier alone.

**compiler-version.** Lua and LibTomCrypt/LibTomMath were built unoptimised (-O0), and Lua's debug information names a Nintendo clang 5.0.0 snapshot rather than the 5.0.1 fork used for the rest of the game. Unoptimised code mirrors the exact compiler build, which we do not have, so these drift by a few instructions (extra parameter copies and spills) whatever the source says. The source is the upstream library source. This is the best explanation, not a proven one.

**register-allocation.** Register allocation is the compiler's choice of which CPU register holds each value. Here the original and ours compute the same thing with the same (or nearly the same) instructions, but in different registers, sometimes with an extra move or a value spilled to the stack.

**instruction-scheduling-or-pairing.** The same operations are issued in a different order, or two loads/stores are combined into one paired instruction (ldp/stp) in one build and not the other.

**block-placement-or-tail-merge.** The same blocks of code are laid out in a different order in memory, or the compiler merged/duplicated a shared tail (such as a common return path) differently.

**folding-or-instruction-choice.** The same logic, but the optimiser folds, combines or reuses a comparison or calculation differently, or picks a different instruction for it: a branch turned into a branchless select (csel/cset), two tests merged into one, a repeated load or call shared, a byte load instead of a halfword load, a bit test instead of a compare. The values tested and the results are the same.

**unexplained.** Written and examined, but no cause has been identified, or the notes do not say.

**compiler-pass.** One specific optimisation step in the original compiler (a vendor fork of LLVM 5.0.1) transforms this code differently from ours: for example InstCombine folding a pointer cast into a second copy of a loop variable in the DemonWare socket-router loops, or GlobalOpt splitting a static. The source is believed right; the difference is in the compiler.

**header-version.** The difference sits inside code inlined from the shared blz container headers (vector.h, string.h). Our copy of those headers is evidently a slightly different version from the one the game was built with (different growth or reload sequences), and changing them affects hundreds of files, so it was left alone.

**inlining-decision.** The compiler copied a small helper into this function (inlining) where the original called it, or the reverse. The work done is the same; the code size and call list differ.

**loop-transform.** A loop is reshaped differently: rotated, unrolled, unswitched or vectorised in one build and not the other.

**sdk-runtime.** Nintendo SDK startup code, not game code. It is excluded because defining it in our build changes how the program links; the original SDK object provides it.

**stack-layout.** The same values are kept in different stack slots (one shared slot in ours, two in the original, or a different frame size). The code does the same work.

**lambda-numbering.** The compiler numbers anonymous lambdas ($_0, $_1, ...) per file. Ours gives this lambda a different number, so the symbol name differs although the code is emitted.

**tls-checker-limit.** A limit of the comparison tool, not of the code: ours keeps the object-file form of a thread-local variable access and the original has the form the linker rewrites it to.

**no-evidence.** Nothing in the debug information or the binary supports writing it.

**checker-cannot-identify.** Excluded: a static helper with no debug information whose name is shared with another file, so the comparison tool cannot tell which is which. The source is present and compiled.

**rough-draft.** A rough first version (often from decompiler output) that was never brought close; the difference has not been analysed.
