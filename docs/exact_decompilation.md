# Full exact decompilation: operating plan

Owner decision, 2026-11-01: finish complete exact binary matching before desktop
recompilation. This supersedes the earlier native-first plan. Preserve the native
harness and staged source, but do not spend this campaign on desktop backends,
gameplay-port work or runtime substitutes.

## Completion contract

The target is the pinned Diablo III Switch 2.6.2 original executable in
`config/original_inputs.json`. All 36,559 indexed functions, original data and
unnamed binary ranges remain in scope, including SDK/middleware and the 2,439
currently unattributed functions. A guessed implementation, opaque original-code
blob, missing owner or approved exception cannot count as completed decompilation.

Completion requires independently reviewed reconstructed source and a clean,
reproducible build that matches the original executable byte for byte. Report
decompressed load segments and original NSO container/metadata comparisons
separately; matching one does not prove the other. Do not exclude padding,
relocations, unwind, initialization, TLS, imports, linker-generated bytes or
container fields merely because they are outside the function inventory.

The current shared comparison ELF permits unresolved imports and contains a
synthetic anchor. The function checker also normalizes some address and trap
differences. These are useful intermediate tools, not the final artifact verifier.
Original layout, linker order and packaging reconstruction remain required work.

M is source staging. Existing O and tier-1 O are retained claims, not final
certification. The later whole-image verifier must reject unexplained differences
even when every function has an O label. Current acceptance and promotion gates
remain in force: the canonical-recipe changes proposed below are not implemented
or permission to ignore a failing check.

changes. Observations are not a new whole-project certification.

| Latest curl candidate: 13,670 normal OK / 2,167 mismatches; 14,043 Lua OK / 1,794 mismatches | A successful comparison build is not a green exact baseline |
| 1,525 existing O identities fail in each mode; 3,050 proof-debt mode rows | Reconcile actual shared causes; do not advertise the O total as fresh proof |

The largest observed build allocation categories were recovery-land (44 GiB),
two tier-1 receipt collections (16 and 9.1 GiB), and a prototype review pilot
(6.4 GiB). Earlier runs hit disk-full incidents and large pruning passes; some
required artifacts are now absent. Logs also showed genuine header conflicts and scope,
vtable or unrelated-consumer failures. Those are deterministic prerequisites,
not transient infrastructure errors to retry unchanged.

A bounded metadata-only scan of the completed curl group found 6,000 present
receipt entries with 2,145,593,676 logical bytes; declared hash/size duplicates
account for 1,615,072,566 bytes. Source/support/build copies outside those
manifests are excluded. Hashes were not recomputed and APFS sharing was not
measured, so this is a deduplication opportunity estimate, not reclaimable space
or proof. The broader sample hit its 120,000-entry bound and was dominated by
missing files; it cannot estimate project-wide savings.

## Operational protection implemented now

The cooperating entry points are `receipts.py build --run`, single/group recovery
landing, `build.py`, `try_file.py`, and direct `backends.py --prepare-lua` /
`prepare_lua()`. They acquire a per-user host-wide nonblocking lease before
creating build output or beginning compiler work. Nested landing-to-receipt and
build-to-bootstrap calls can reuse their own lease. Different outputs and clones
cannot acquire separate cooperating build slots. The lock inode is retained;
do not unlink it to bypass a busy build. Process exit releases the kernel lock,
but a daemon-owned Docker container can survive abrupt host-process death. Heavy
entry points now also use a [durable Docker session guard](docker_admission.md).
An interruption leaves a pending marker that blocks replacement work; successful
sessions must confirm the original daemon and no recognized active project
containers before clearing it. Unresolved sessions require explicit reviewed
reconciliation. Never interpret an available host lock as proof all previous
compiler processes stopped; untracked/earlier daemon work remains a limitation.

Capacity estimates use available filesystem bytes and conservatively account for
potentially shared storage pools. Current defaults are 8 GiB additional phase
growth plus a 12 GiB reserve, with 2 GiB growth rechecks before new receipt attempts;
single-object preflight uses a 128 MiB growth estimate. These are deliberate
headroom estimates, not measured upper bounds. Increase them through reviewed
configuration as artifact sizes grow; do not routinely lower the reserve to make
an otherwise inadmissible job start. Completed checkpoints remain authenticated
and intact when a later attempt is denied.

The standalone assessment and receipt preflight/verification are read-only and
do not acquire a build lease. For example, from the repository root:

```sh
python3 tools/resource_admission.py --reserve-bytes 12884901888 --request "$PWD/build" 8589934592
```

Project builds and the host Lua-bootstrap entry point default to two workers;
explicit `--jobs` / `--lua-jobs` values are bounded to 1–8. More workers require
measured memory headroom, not just spare CPU cores. Failure diagnostics now retain
compiler/container exit status and unfiltered failure output. A resource refusal
is an infrastructure condition, not a function mismatch or a failed code hypothesis.

Limits remain explicit: this lease only controls participating same-user tools;
manual Docker commands, other users and unrelated services can still consume
resources. Filesystem checks do not reserve blocks, continuously monitor a running
compiler, or prove Docker VM free space, quotas or RAM. Direct low-level bootstrap
commands are not substitutes for the guarded host entry point. Keep full-build
concurrency at one on the observed VM. No existing receipt, original, compiler,
claim, worktree or unrelated service was deleted/stopped by this change.

## Required work, in priority order

### First implementation checkpoint — 2026-11-01

Two independently reviewed diagnostic tools are now available:

- [Artifact storage](artifact_store.md): immutable compressed snapshots with
  actual hash verification and exclusive restoration. Two real mode receipts
  totaling 536.6 MB occupied an 80.6 MB store; both restored copies passed the
  retained-mode verifier. Complete-bundle
  relocation, eviction, quotas and automated retention remain unimplemented.
- [Whole-image comparison](exact_image.md): literal pinned NSO comparison and
  separate decoded-segment diagnostics. Real checks distinguish matching decoded
  segments from different container bytes. Source lineage and final artifact
  acceptance remain outside this diagnostic tool.

The focused suite has 39 tests: 38 pass and one filesystem-specific case skips on
this host. Real storage and image pilots supplement those tests.
There were no source-quality promotions or changes to existing acceptance gates.
P26, P27 and P28 remain partial.

### Follow-up: complete receipt recovery and interrupted sessions

The next storage pilot recovered the complete curl-pair receipt root: 17,513 files
and 2,307,607,872 logical bytes. The compressed archive, independent compact
restore and pinned tools used about 706 MiB together. The unchanged
group verifier passed in an isolated container that mounted only the
restore, pinned tools and pinned NSS at the required paths. It had no access
to the original receipt tree. Every restored file was checked again afterward.
This proves retained-evidence recovery for that bundle, not a fresh build or
strict source acceptance. General retention/eviction
policy and external dependency archival are still required.

The Docker session guard now retains a durable interruption marker, checks known
active project containers and refuses replacement work until reviewed reconciliation.
Its limits and explicit retry procedure are in [Docker admission](docker_admission.md).

A default-off backend experiment prevents a specific O0 DAG combine from
discarding unused frame loads. With it on, `callallgcTM` strictly matches and
`f_luaopen` reaches its original size; across the 40 `lstate`/`lgc` functions the
default strict result was 13 exact, 27 unsupported and zero size mismatches. This
does not grant source or canonical-recipe acceptance.

### 1. Sustainable evidence and failure handling — P26

Keep the admission guard and extend the tested opt-in content-addressed store
to a complete retained-evidence lifecycle. Receipt
manifests must still resolve to authenticated bytes. Any packaging, compression,
copy-on-write or deduplication scheme needs successful restore-and-reverify tests
before replacing originals. A storage saving is not allowed to create proof debt.

Separate active work, accepted proof, failed investigations and regenerable
scratch. Never infer expendability from age, an O label or Docker's reclaimable
label: pinned images/backends and pruned earlier proof may be indispensable.
Start cleanup with a manifest of exact paths, retention roots, recoverability and
references; preserve source commits, reviews and failure diagnostics. No broad
`build/` deletion, Docker system prune or claim release is an archive policy.

Extend conservative interruption reconciliation with high-water accounting,
peak-size measurements and an explicit stop condition
before the next job, plus monitored resource failure classification. Check host
and Docker capacity separately. An offline archive on additional storage is an
option only after its restore path is tested.

### 2. Canonical compiler recipes — P27

The current two-mode policy blocks real Lua exact progress: retained recovery of
267 Lua functions yielded zero normal-mode matches and 250 patched-backend
matches. The prepared lstate/lgc pair similarly has 40 normal size mismatches,
versus 12 strict object matches and 26 relocation-only unresolved cases in Lua
mode, with two residual size differences. Neither upstream similarity nor the
patched compiler alone proves correctness.

Build a per-original-CU manifest of compiler/frontend/backend, headers, defines,
language/ABI flags, optimization, tools and linker provenance. Unknown recipes
stay unknown. Calibrate with minimized real-owner fixtures for C/C++, signedness,
Lua O0 unused-value reloads/spills, varargs, switches, data and unwind. Preserve
existing proven results and independently review compiler changes.

The proposed policy is one authenticated canonical recipe for each original CU,
with other modes retained as diagnostics/regression experiments. Implement and
review that policy explicitly; do not silently remove the stock or Lua gate.
Artificial source spills, register pinning or assembly stand-ins are not a
compiler-recovery strategy.

### 3. Whole-artifact verification and shared proof failures — P28/P29

Integrate the literal artifact comparator with source-bound final acceptance and
build a full original-range manifest, so no unnamed material disappears from the
denominator. Recover original layout,
link order, entry points, imports, registration/initialization and packaging.

Group proof debt by actual missing definition/reference mechanism. Current mode
rows include 1,518 unknown-original-GOT, 912 rebuilt-undefined-GOT, 320 indirect
flow, 294 jump-table and six original-undefined-GOT cases. These are not distinct
function counts. Fixing one authentic dependency can unblock many callers.

Distinguish code differences from unsupported verification. Extend local-call,
qualified-name, string/constant/global, switch-table, relocation and unwind
proofs with wrong-owner/target/extent/alignment negative tests and real retained
pilots. Reproduce missing earlier evidence before claiming it is verified.

The prepared Lua pair is a concrete calibration/proof package: ten lstate and
thirty lgc functions, an 18-byte error literal and four relative tables with
5/7/7/5 entries. Commits `d74c820` and `6095561` remain staged and claimed, not
exact-complete. The initial size-qualified report exposed 62 local calls; complete
object accounting finds 63 (8 in lstate, 55 in lgc), plus two local function-address
ADRP/ADD pairs. All 24 table slots remain in scope. The two prior size gaps are
removed by the isolated compiler experiment above. External references, data/link
witnesses, recipe approval and whole-consumer checks remain. Use this evidence to resolve
shared prerequisites; do not launch repeated rejected full builds.

Owner-scoped resolution of section symbols plus addends to unique function
entries now proves those calls and address pairs. Wrong-owner, ambiguous and
interior targets are rejected. The two `strchr` calls also have bounded original
PLT/import-chain witnesses: PLT `0xc1d4e0`, GOT `0x10e4400` and JUMP_SLOT (1026)
for undefined `strchr` with zero addend. Candidate linked import binding remains
unproved; no function inventory entry is invented. The complete 18-byte merged
string and its consumer pair now have a non-admitting witness. The four PREL32
tables totaling 96 bytes also have complete slot, target and dispatch witnesses;
bounds are conditional on entry through the recognized guard, not a whole-program
control-flow proof. An isolated wrapper regenerates the witnesses and reconstructs
the ten address relocations, yielding all 40 exact instruction comparisons.
Next prove original data allocation/shared consumers and candidate linked placement
and imports. Existing recovery data gates still reject these string/table sections.
A new relocation type cannot simply be added to a 64-bit data proof path. Object-level FDE programs,
ranges and CIE bytes match for all 40 functions, but candidate linked unwind and
its authenticated object/source routing remain unproved.
None of these unresolved classes can be treated as a match merely by masking
their relocation bits.

### 4. Dependency-ready jobs and reuse — P31

Use existing address/owner IDs. A job packet must bind:

- Baseline commit, exact original membership and address-plus-qualified names.
- Original/NSS and canonical recipe hashes; authentic source/type/helper evidence.
- Allowed source/header/data edits and a complete affected-consumer manifest.
- Typed prerequisites: ownership/layout, helper definition, data, compiler,
  verification support and resources; each has evidence or an explicit blocker.
- Expected emissions, object preflight, full link/data/unwind checks, independent
  review, integration and final-artifact obligations.
- Known failed hypotheses, attempt/time/storage budgets, retained output paths and
  a specific resume condition. A changed baseline revalidates affected evidence.

`project_plan.py --actionable` is a backlog filter, not dependency readiness or
dispatch authorization. An all-O owner is not automatically artifact-certified.
Suggested job stages are evidence-ready, source-prepared, object-proven,
link/data-proven, independently-reviewed, integrated and artifact-certified;
resource-wait and blocked require separate reasons.

Run cheap pinned-recipe source and affected-consumer checks before full receipts.
The duplicate-enum compile failure and Domino helper regression show why
consumer closure matters. About eight distinct evidence-backed hypotheses is a
stop point, not eight identical retries. Preserve useful source and resume only
when a named prerequisite or hypothesis changes.

Raise the whole-owner cap modestly where complete accounting is simpler than
subsets. A 96-function cap would make 29 unqualified owners with 2,104 U functions
size-eligible, but does not resolve their other blockers. Qualified locals such as
`body@lparser.c` require correct identity mapping, not stripping the suffix.
Larger owners need bounded drafting plus whole-owner omission/extra checks.

Separate compilation-cache keys from checker-result keys. Compilation keys bind
the actual dependency/preprocessed inputs, compiler/image/recipe, generated inputs
and relevant environment. Result keys additionally bind original inputs, checker,
policy and requested identities. Revalidate restored bytes; retain final full
linking and comparison at integration checkpoints. Tool changes should recheck
unchanged compiled inputs where valid, rather than forcing needless recompilation.
These reuse policies require implementation and review; current receipts still
require their existing fresh builds.

## Measurement

Track newly fully proven identities/original bytes, completed owners, eliminated
shared blockers, remaining proof categories, final-artifact differing ranges,
review backlog, retries, build/review time and retained/unique storage. Keep M,
existing O, fresh checker OK and full artifact certification separate. Function
percentages alone do not support an ETA.
